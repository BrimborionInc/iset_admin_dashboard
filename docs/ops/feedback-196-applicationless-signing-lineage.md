# Feedback 196 Applicationless Signing-Lineage Repair

Status: **PROD NO-GO.** The first implementation and its TEST acceptance were re-audited before promotion and found incomplete. Corrective implementation and a new exact-source TEST qualification are required. PROD remains unchanged and read-only.
Last updated: 2026-08-25.

## Reported journey

A Regional Manager attempted the post-approval communication step for case `76`, application `123`. The application has a final approved review and application-owned Action Plan `184`, but the same long-lived case also retains applicationless Action Plan `3` and sent CFA version `19`. The secure-message request failed with `cfa_version_application_scope_unknown` before the decision-letter/funding-form package could be sent.

The defect is not that applicationless history exists. The defect is that a case-wide safety check let unrelated historical provenance veto a consequential operation whose application and Action Plan were already known exactly.

## Controlling behavior

- CFA and Financial Overview series remain case/template owned, with continuous case-series version numbers. A repeat application creates the next version; it does not start a new series.
- New CFA versions record nullable typed `application_id` and `action_plan_id`. New Financial Overview versions record nullable typed `application_id`. Historical rows are not guessed or backfilled.
- A populated typed version owner is authoritative. Snapshot JSON is a compatibility fallback only when the corresponding typed owner is `NULL`; populated snapshot data may confirm a typed owner but may not contradict it.
- Creating or sending a CFA resolves the exact selected application and Action Plan first. Its intervention snapshot comes only from that plan. The route uses the identity returned by the fresh version creation and does not search again for another draft.
- Version numbering and the read-only latest-signed redline baseline remain case-series-wide. Withdrawal and signing-request cancellation are limited to unsigned versions in the exact selected application/Action Plan lineage for CFA, or exact selected application for Financial Overview.
- Applicationless and sibling versions remain readable history. They are not changed and cannot veto unrelated application work. A contradiction inside the selected typed lineage still stops only the unsafe form operation.
- A missing Action Plan is an operation prerequisite, not evidence of corrupt lineage. Multiple eligible plans require an exact selection. Neither condition makes the case or ordinary secure messaging unusable.
- Portal completion locks and validates only the requested version, its case series, linked message/application, participant, generated document, schema metadata, and—when typed—the exact Action Plan. It does not scan sibling or applicationless versions.

## Policy boundary

This repair does not settle when the business should create additional Action Plans or permit concurrent plans. That remains under `WP-13`. It preserves that uncertainty by requiring an existing exact plan for a CFA rather than silently choosing among several or classifying all multiplicity as data corruption.

The blocked operation is limited to generation/send or completion of the affected versioned form. Staff may still send an ordinary message, work on sibling applications, and use unrelated case functions.

## Required evidence

Acceptance uses ordinary product tests and the real Express route, followed by an explicit deployed TEST journey. The retired general/CFA qualification harness is not used, repaired, or replaced.

No PROD case, application, Action Plan, CFA, signing, message, document, feedback, configuration, schema, or deployment mutation is authorized by this work.

## Pre-PROD release re-audit

The first TEST result below is retained as historical evidence, not as promotion evidence. It proved that an explicit `actionPlanId` request could bypass unrelated applicationless CFA history. It did not reproduce the normal Coordinator approval-letter caller, which omitted that field, and its fixture did not include the exact application/Action Plan draft created by final approval. The ordinary lifecycle would therefore have withdrawn the approval-created v1 and sent a duplicate v2. That candidate must not be promoted.

The re-audit also found that generic Case Workspace compose inherited the currently selected Action Plan and intervention as hidden send authority. A browsing selection could therefore turn an ordinary application communication into a different scoped operation or trigger a false mismatch block. Scope selection must now be visible and deliberate: ordinary messages carry neither value; an intervention follow-up requires confirmation; a direct funding agreement with multiple exact open plans requires a visible choice; the server remains authoritative if the plan-list read fails. A failed plan-list read must not create a fetch loop or disable an otherwise valid server request.

Draft reuse needs a narrower rule than either “always rebuild” or “reuse any exact draft.” An exact draft may be reused only when its stored snapshot still matches its own hash, a fresh snapshot for the exact Action Plan, and the same latest signed case-series baseline. It must never be silently rebased by changing `supersedes_version_id`, because that would change lineage without rerendering the redline. A stale, corrupt, or differently based draft is replaced with a freshly rendered exact-plan version.

The applicant portal also froze the submitted payload before lineage completion but did not return that frozen body on reload after a retryable completion failure. The applicant could then unknowingly post schema defaults and receive a permanent payload-mismatch block. Pending/viewed requests with a valid frozen payload must resume that exact body; malformed or partial frozen state is a non-retryable staff-repair condition; already signed requests remain readable.

Two operational release gaps were found as well. The normal deployment migration runner did not dispatch this guarded migration through the bounded executor and would have made PROD the first normal-path raw execution. Clear Test Data also disabled foreign keys, omitted version tables, used the wrong deletion order, and mixed implicit-commit `ALTER TABLE` statements into its transaction. Both are release blockers: canonical migration dispatch must use the same reviewed executor in TEST and PROD, while Test cleanup must be DML-only, dependency-complete, and rollback-safe.

Promotion evidence must therefore be regenerated from a clean source candidate and must include the real approval caller with no explicit plan, reuse of the approval-created exact draft without a version bump, multiple-plan visible selection, ordinary messaging despite unrelated bad history, portal submit/failure/reload/resubmit of the exact frozen body, exact-plan delete behavior, cleanup rollback behavior, and the canonical TEST migration dispatch. The retired qualification harness remains prohibited and is not part of this plan.

The last hostile pass deliberately tested where broad “safety” logic had previously made unrelated work unusable. It found and corrected four additional boundaries before any `r2` deployment:

- Portal participant authority now treats a populated current client Cognito subject as authoritative, but treats `NULL`, empty, or whitespace legacy links as genuinely unlinked. An exact application submission participant—or immutable typed participant for an applicationless request—remains a compatibility fallback only in that unlinked state. A populated link to another participant still stops the exact signing request.
- Generic portal signing now locks case, client, application, and participant authority before object upload. Object creation, document materialization, supporting-document linkage, event/fan-out, and request completion share the caller-owned transaction. The event call carries top-level case identity as well as the query executor, so it cannot silently use the global pool. A failure after event creation rolls back every database effect, compensates the object, and an unchanged retry creates one final event.
- Historical secure-message attachments no longer become unavailable because their optional application differs from the currently selected application or because best-effort document indexing fails. Authorized reads prove hard case/client/applicant ownership first, preserve existing other-source/non-ownership document lineage, skip unsafe adoption, and return the attachment. Exact historical rows produced by the earlier applicant-relink adoption bug are recognized without rewriting them. A proven hard ownership contradiction still blocks disclosure before any adoption write.
- Ordinary replies may continue to the immutable typed participant on a historical conversation after a case-account relink. A reply that adds a signing form is different: the transaction rechecks that the historical recipient is still the exact current case participant and otherwise asks staff to start a new message. This prevents sending a consequential form to a former account without blocking text-only case history.

A subsequent hostile pass rejected another intermediate checkpoint. Blank Cognito values on both `client` and shared `user` rows could join each other as if they were a real identity, while a populated client subject with no matching shared user could be mistaken for an unlinked account and fall through to the application's historical submission user. Every active participant join now excludes blank values explicitly, carries the raw client-link evidence into the resolver, permits the exact-submission fallback only for a truly `NULL`/blank client link, and returns the narrow `applicant_account_link_unresolved` repair result for a populated unresolved link. PROD metadata proves `user.cognito_sub` and `client.applicant_cognito_sub` are unique; the read-only pending-request inventory found no populated unresolved or mismatched current request, but the branch remains protected for future drift.

The same pass exercised asynchronous browser interleavings introduced or touched by this release. A delayed reply-status acknowledgement can no longer clear attachments or display success after the applicant has navigated to another reply target. A delayed signing response can no longer mark a newly opened document as submitted, replace it with the former document's error, or continue retrying the former request. Disabled messaging guidance distinguishes an unassigned case from a missing staff-user mapping and is not shown in Deleted items. Each case has a deferred-promise navigation regression.

The release-control audit separately rejected TEST deployment until all remote staging occurs after a durable manifest and local admission, retired harness files are absent from real archives, the exact detached clean sources are enforced, and a two-application TEST install can automatically restore both previously running applications after any partial failure. The earlier dirty `r1` artifacts are not trusted as rollback sources. PROD remains blocked additionally by existing `EA-028`; this work does not authorize or perform a PROD change.

These corrections are backed by both permissive and restrictive regressions: applicationless history, sibling applications, unlinked/blank legacy identities, old typed participants, attachment application differences, index failure, and text-only historical replies remain usable; concrete participant or hard ownership contradictions stop only the affected form or disclosure boundary, and every injected failure proves rollback/no residue.

The final maintained local gate passed `103` admin frontend suites / `637` tests and `68` backend/tooling suites / `767` tests (`1,404` total), plus `20` portal frontend suites / `97` tests and `297` portal backend tests (`394` total). Admin and portal lint and production builds passed; the admin privacy-route check, server/deploy/migration syntax checks, and both repository diff checks passed. The release-control failure-injection set passed `12` suites / `149` tests, including a final `3`-suite / `75`-test rerun after the last change. The maintained aggregate no longer requires retired qualification utilities to be packaged; no retired qualifier was run or repaired.

These are local source gates, not deployed acceptance. A clean committed source candidate and new TEST deployment/product journey remain mandatory. No corrected `r2` TEST deployment has occurred at this point in the ledger, and PROD remains **NO-GO** and untouched.
