## Operating Boundary

- This register is the cross-system index and decision ledger. Keep detailed domain evidence in the relevant canonical audit or planning document and link it here instead of copying it.
- Code, tests, schema/migrations, runtime configuration, and verified environment evidence outrank narrative documents. Historical plans and change requests establish intent only.
- An audit pass investigates and records findings; it does not change application behavior. Implementation requires a separate explicit task that revalidates the finding first.
- This register does not replace the live Bugs and Change Requests queue, product plans, release tracking, or specialized security/operations registers. Link an approved finding to those systems when it becomes implementation work.
- Do not turn style preferences, speculative rewrites, generic modernization advice, or file size alone into findings. A design finding must demonstrate a concrete correctness, security, operability, testability, or sustained-change-cost consequence.
- Preserve existing finding IDs from specialist audits. New cross-system findings created here use sequential IDs `EA-001`, `EA-002`, and so on.
- Environment checks are read-only during audit work and must follow `docs/ops/agent-operational-access.md`. TEST/PROD mutations remain outside audit scope unless Bill separately authorizes them.

## Evidence Standard

A confirmed finding must contain all of the following:

1. **Concrete source evidence:** exact repository, file, symbol/route/query/migration/config key, and reviewed revision or date.
2. **Complete behavior chain:** entry point, trust or state transition, downstream consumer, and relevant frontend/backend/database or cross-app boundary. A suspicious line in isolation is not enough.
3. **Failure or risk scenario:** realistic preconditions, the incorrect outcome, and who or what is affected.
4. **Contradiction or invariant:** the test, schema constraint, documented business rule, security boundary, API contract, or internally inconsistent behavior that establishes why the outcome is wrong.
5. **Current-state reconciliation:** search existing audits, plans, tests, live feedback/backlog sources, and recent fixes so a resolved issue is not reopened from stale evidence.
6. **Verification direction:** the smallest test, reproduction, query, trace, or environment check that can prove the finding and later prove its repair.

Evidence strength is recorded separately from severity:

| Strength | Required proof |
| --- | --- |
| `verified` | Reproduced with a focused automated test, browser/API trace, safe database query, runtime observation, or equivalent direct evidence. |
| `code-confirmed` | A complete deterministic source/schema/config path proves the behavior, but it has not yet been reproduced in a running environment. |
| `candidate` | Evidence is incomplete, ambiguous, stale, or missing a downstream impact chain. Keep it in the investigation queue; do not count or prioritize it as an open finding. |

Claims about third-party behavior require current authoritative documentation or approved sandbox evidence. A local mock or remembered vendor contract cannot prove external fidelity.

## Severity Scale

Severity measures demonstrated impact, not implementation effort, confidence, or scheduling priority.

| Severity | Threshold |
| --- | --- |
| `critical` | Credible path to broad unauthorized sensitive-data disclosure, irreversible or widespread business-data loss/corruption, complete production unavailability, or an unsafe financial/security action with immediate material impact. Escalate immediately rather than waiting for cycle synthesis. |
| `high` | Core workflow failure, unauthorized object access, material state corruption, repeated incorrect financial/program decisions, or a release/rollback defect likely to affect multiple users or cases. |
| `medium` | Real but contained correctness, privacy-minimization, performance, reliability, or maintainability problem with a practical trigger and recoverable impact. |
| `low` | Narrow impact, strong mitigating controls, or design/test debt with a demonstrated change-cost or future-defect consequence but no current material failure. |

Priority is assigned only during synthesis after considering severity, likelihood, reach, dependencies, fix risk, and business timing. Do not inflate severity to force prioritization.

## Finding Lifecycle

| Status | Meaning and exit condition |
| --- | --- |
| `candidate` | Investigation is incomplete. Promote only after the evidence standard is met; otherwise reject or link to the correct existing item. |
| `open` | Evidence is `verified` or `code-confirmed`, severity is assigned, and no disposition has been approved. |
| `planned` | The finding has an agreed fix boundary and implementation destination or release plan. |
| `in_progress` | Authorized implementation is underway. Link the working plan/thread artifact. |
| `verification_pending` | The fix exists, but required regression, environment, migration, or deployment proof is incomplete. |
| `closed` | Root cause is fixed and required verification is recorded. |
| `accepted` | The behavior is understood and deliberately retained with owner, rationale, and review trigger. |
| `deferred` | Valid finding intentionally postponed with rationale, dependency, owner, and recheck condition. |
| `rejected` | Investigation disproved the claim or established that it is preference-only. Preserve the rejection reason to prevent rediscovery. |
| `duplicate` | Another canonical finding owns the issue. Record its ID/link and do not maintain two statuses. |

Normal flow is `candidate -> open -> planned -> in_progress -> verification_pending -> closed`. `accepted`, `deferred`, `rejected`, and `duplicate` are explicit disposition paths, not silent deletion.
