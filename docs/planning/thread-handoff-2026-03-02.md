## High-level product direction
Primary redesign focus is payment packet scheduling and queue behavior.

Current problem statement:
- Payment packets are perceived as auto-generated by-products of intervention approval.
- Users need a forward-looking operational queue that shows what must be sent to Finance and when.

Target model:
- Queue is schedule-driven.
- Packets are grouped by scheduled payment date within intervention boundaries.
- Queue must show upcoming + due + overdue + sent history in one timeline-oriented view.
- Manual human trigger remains part of workflow for submissions to Finance.

## Locked decisions (payment scheduling)
These are agreed and should be treated as implementation requirements.

1. Aggregation key
- Group packet lines by `intervention_id + scheduled_payment_date`.
- Do not group lines across interventions even if dates match.

2. Creation trigger
- Keep current trigger point: create scheduled draft packets on intervention approval.
- Do not move packet persistence to proposal-stage drafting.

3. Recurrence materialization
- Generate all recurrence occurrences at approval time (example: all 12 monthly entries queued immediately).

4. Recurrence date semantics
- Occurrence 1 uses recurrence `startDate`.
- Remaining occurrences step by configured cadence (`weekly`, `bi_weekly`, `monthly`, `quarterly`).
- Treat as period-start schedule dates.

5. Queue visibility timing
- Generated packets should be visible immediately after creation.
- Users must be able to see what needs manual triggering.

6. Manual trigger workflow
- Keep manual trigger as a discrete release step.
- Recommended status flow:
  - `draft_scheduled` or `awaiting_trigger` -> `released` -> `sent` -> `posted` -> `reconciled`
- `released` means user-triggered and ready for finance submission.

7. Due/overdue indicators
- Use strict calendar date logic (no grace period):
  - overdue if scheduled date is before today and packet not terminal
  - due today if equals today
  - upcoming if after today

8. Regeneration policy after approval edits
- Rebuild unsent packets when funding/schedule changes.
- Preserve immutability for sent/posted/reconciled records.
- Record audit footprint for regenerations.

9. Defensive guards
- Add lightweight backend safeguards for non-UI paths (direct writes, scripts/imports).
- Keep them minimal; UI already has strong guard rails.
